# Agent 模糊输入澄清策略测试方案

日期：2026-07-23

适用分支：`dev-agent`

状态：待执行

测试对象：真实火山方舟模型 + TodoList 后端 HTTP API

---

## 1. 背景与动机

### 1.1 触发问题

用户输入：

> 给我安排明天9点的会议，是和HR谈薪水

Agent 实际生成的确认卡片：

| 字段 | 实际值 | 问题 |
| --- | --- | --- |
| `text` | 和HR谈薪水 | ✅ 正确 |
| `time_start` | `2026-03-28T09:00` | ❌ "明天"应为 2026-07-24，实际解析为 3月28日 |
| `time_end` | `2026-07-23T12:30` | ❌ 用户未提供结束时间，Agent 凭空编造了 12:30 |
| `priority` | medium | ⚠️ 可接受 |
| `category` | work | ✅ 合理推断 |
| `notes` | null | ✅ 正确（用户未提供） |

**三个明确错误**：
1. **开始日期错误**：将"明天"（2026-07-24）解析为 2026-03-28
2. **结束时间编造**：用户只给了"9点"，Agent 自行补充了不存在的结束时间 12:30
3. **结束日期荒谬**：结束日期 2026-07-23（"今天"），早于开始日期 2026-03-28

### 1.2 核心问题

Agent 在面对**信息不完整**的输入时，正确行为应当是：

```
信息不完整输入 → 识别缺失字段 → 反问用户 → 用户补充 → 生成准确卡片
```

但实际行为是：

```
信息不完整输入 → 静默猜测/编造 → 生成错误卡片
```

### 1.3 本文档目标

本方案专门测试 **Agent 面对模糊、不完整、有歧义输入时的澄清策略**。核心验证：

- Agent 能否识别输入中**缺失的关键信息**？
- Agent 能否识别输入中的**歧义**（一种表达对应多种合理解读）？
- Agent 能否识别输入中的**矛盾**（两部分信息逻辑冲突）？
- 在以上情况下，Agent 是**反问澄清**还是**静默猜测**？
- Agent 的反问是否**精准**（只问必要信息，不问已知信息）？
- 澄清后，Agent 能否**正确使用补充信息**生成卡片？

---

## 2. 澄清行为分级

| 等级 | 名称 | 定义 | 示例 |
| --- | --- | --- | --- |
| **C0** | 静默编造 | 信息缺失时，不询问就填入虚构值 | 用户未给结束时间，Agent 填入 12:30 |
| **C1** | 静默假设 | 信息缺失时，不询问就用默认值 | 用户未给结束时间，Agent 填入 null（这是合理的默认） |
| **C2** | 主动澄清 | 信息缺失时，主动反问用户 | "请问会议预计几点结束？" |
| **C3** | 精准澄清 | 反问时明确指出缺失项，并给出上下文 | "明天9点和HR谈薪水的会议，请问预计多长时间？还是只记录开始时间？" |
| **C4** | 智能推断+确认 | 给出合理推断，同时征求确认 | "明天9点开始。结束时间没提到，我先不填。如果后续需要补充，随时告诉我。" |

**及格线**：C1 及以上（不编造）。**目标**：C2 及以上。

---

## 3. 缺失信息分类

Agent 可以处理的待办任务有六个字段：`text`、`priority`、`category`、`time_start`、`time_end`、`notes`。

### 3.1 字段的"可缺失性"

| 字段 | 默认行为 | 缺失时是否需要澄清 |
| --- | --- | --- |
| `text` | 无默认值，必须提供 | **必须 CL**（无法创建无标题任务） |
| `time_start` | 可为 null | **看语境**：若用户意图明显需要时间（"安排会议"）但未提供，应 CL |
| `time_end` | 可为 null | **不应编造**：用户未提及时默认 null，不应自行补充 |
| `priority` | 可为 null → 系统默认 medium | 不需要 CL（使用系统默认值即可） |
| `category` | 可为 null → 系统默认 other | 不需要 CL（使用系统默认值即可，或合理推断） |
| `notes` | 可为 null | 不需要 CL（用户未提则 null） |

### 3.2 关键缺失 vs 可接受缺失

**关键缺失**（必须 CL）：
- 任务标题完全缺失
- 时间表达有歧义（"晚点""回头""有空时"）
- 日期表达有歧义（"下周三"在周三说时有歧义）
- 用户明确要求的时间但用了模糊表达

**可接受缺失**（允许合理默认值）：
- priority / category（系统有默认值）
- notes（默认为空）
- time_start / time_end（允许无时间的任务）
- 非用户明确要求但Agent推断的字段

### 4.1 时间缺失类（12 条）—— 对应触发 bug

#### TM-001: 只有开始时间，无结束时间（触发 Bug 复现）

```
【输入】"给我安排明天9点的会议，是和HR谈薪水"
【执行条件】D0=2026-07-23
【错误行为】time_end 填入虚构值（如 12:30）
【正确行为】
  - 方案A（C2）: "请问会议预计多长时间？还是只记录9点开始？"
  - 方案B（C1）: time_start=2026-07-24T09:00, time_end=null，并在回复中说明未设结束时间
【验证】
  - time_start 必须为 2026-07-24T09:00
  - time_end 必须为 null（不得为任何非 null 值）
  - 若 CL，反问应明确针对"结束时间"
【等级要求】≥ C1（time_end 不许编造）
```

#### TM-002: 只有日期，无具体时间

```
【输入】"8月15号去体检"

【验证】
  - 不允许 time_start=2026-08-15T00:00（静默填入零点）

### 4.5 澄清后的正确执行（6 条）

#### CE-001: 澄清→补充→创建

```
【对话】
  轮1: "帮我安排明天9点的会议，和HR谈薪水"
  [Agent CL: "请问预计几点结束？"]
  轮2: "11点结束"
【验证】
  - 生成1个create
  - time_start=2026-07-24T09:00, time_end=2026-07-24T11:00
  - text="和HR谈薪水"或"会议：和HR谈薪水"
  - 确认后任务字段完全正确
【等级要求】≥ C1
```

#### CE-002: 澄清→补充→修正→创建

```
【对话】
  轮1: "明天下午和客户开会"
  [Agent CL: "请问具体几点？"]
  轮2: "3点吧"
  轮3: "不对，还是4点。备注带上样品。"
【验证】

  - 轮3: supersede旧批次，新卡time_start=D0+1T16:00, notes="带上样品"
  - 最终只创建一个任务，时间4点，备注正确
【等级要求】≥ C1
```

【对话】
  轮1: "帮我记个事"
  [Agent CL: "请问是什么事？"]
  轮2: "算了不记了"
【验证】
  - 不创建任何任务
  - 不生成proposal
  - 不残留pending批次

```

#### CE-004: 澄清→部分补充→部分默认

```
【对话】
  轮1: "明天有个任务要做"
  [Agent CL: "请问具体是什么任务？什么时间？"]

【验证】

  - 或CL进一步确认具体时间
  - 不编造结束时间
【等级要求】≥ C1
```

#### CE-006: 澄清后多个任务信息不同程度完整

【验证】

  - C: 无时间

  - 不编造B和C的时间
【等级要求】≥ C1

## 5. 澄清质量评估维度

对 Agent 的每次澄清行为，从以下维度评估：

### 5.1 澄清必要性判断

| 评分 | 定义 |
| --- | --- |
| ✅ 正确CL | 信息确实缺失/歧义，Agent 正确识别并反问 |
| ✅ 正确不CL | 信息足够或可使用合理默认值，Agent 直接生成卡片 |
| ❌ 漏CL | 信息缺失但 Agent 未反问，静默猜测/编造 |
| ❌ 过度CL | 信息已足够，Agent 仍反问（造成不必要的交互轮次） |

### 5.2 澄清精准度

| 评分 | 定义 | 示例 |
| --- | --- | --- |
| ⭐⭐⭐ | 精准指出缺失项，给出上下文 | "明天9点和HR的会议，请问预计几点结束？" |
| ⭐⭐ | 指出缺失项，无上下文 | "请问几点结束？" |
| ⭐ | 泛泛而问 | "还有什么需要补充的吗？" |
| ✗ | 问已知信息 | "请问是明天吗？"（用户已说"明天"） |

### 5.3 澄清后的卡片质量

| 评分 | 定义 |
| --- | --- |
| ✅ | 用户补充信息后，卡片字段完全正确，无残留编造 |
| ⚠️ | 部分正确，但仍有未解决的编造/丢失 |
| ❌ | 用户补充信息被忽略，或仍使用之前编造的值 |

## 6. 判定矩阵

### 6.1 每条用例的判定

```
PASS:  所有字段值符合预期（无编造值）
       需要CL时确实CL了（或合理使用null默认值）
       澄清后卡片字段正确

FLAKY: 3次执行中至少1次达到PASS标准，但非每次

FAIL:  出现以下任一情况：
       - 编造了用户未提供的值（特别是time_end）
       - 日期解析错误（如"明天"≠D0+1）
       - 应该CL但没有CL
       - 澄清后仍使用错误值
```

### 6.2 严重等级

| 等级 | 定义 | 典型场景 |
| --- | --- | --- |
| S0 | 数据安全或严重误导 | 编造时间导致用户错过真实会议；创建不可能的时间范围 |
| S1 | 字段级错误 | 开始日期计算错误（如触发bug的3月28日）；编造非null的结束时间 |
| S2 | 策略级问题 | 应该CL但选择了静默假设（假设值恰好合理算S2，假设值错误算S1） |
| S3 | 体验问题 | 过度CL（信息足够还问）；反问措辞不够精准 |
